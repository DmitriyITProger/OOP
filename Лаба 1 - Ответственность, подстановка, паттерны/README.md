# Лабораторная работа 1. Ответственность, подстановка, паттерны поведения

Java 21, Maven. Вариант 10 (отчёт `XmlSalesReport`, статус `RETURNED`).

## Что сделано

**1. Тариф без `instanceof`** (`hw01OrderFlow`)
- Добавлен тариф `SameDayDelivery`: 900 руб. при любой сумме, срок 0 дней.
- Знание «это экспресс» и текст обещания клиенту перенесены в сам тариф: методы `express()` и `promise()` в `DeliveryTariff`. Уведомление и отчёт больше не проверяют тип тарифа.
- В пакетах `app` и `infra` (кроме `Main`) названий конкретных тарифов не осталось. Отчёты считают экспресс-заказы обоих видов.

**2А. Отчёт `XmlSalesReport`** (`hw01OrderFlow`)
- Подкласс `SalesReport` с выводом в XML, включая случай пустого хранилища. Хватило существующих шагов шаблона (`header`, `row`, `footer`), новых крючков не понадобилось. `TextSalesReport` и `CsvSalesReport` выдают прежний результат.

**2Б. Статус `RETURNED`** (`hw01OrderFlow`)
- Переход `SHIPPED → RETURNED` через `Order.returnOrder()`, сценарий `ReturnOrder`: заказ сохраняется, клиенту уходит уведомление с возвратом полной суммы.
- Из `RETURNED` переходов нет. Возвращённый заказ считается неоплаченным и в выручку не входит. Запрещённые переходы бросают `IllegalStateException`, статус не меняется.

**3. Банковский счёт** (`hw01bank`)
- `Amount` — значимый объект (неизменяемый, равенство по значению, без отрицательных сумм).
- `Account` — сущность (равенство по номеру). Дебетовый и кредитный счёт созданы фабриками `debit` и `credit` внутри одного класса: вид счёта — это нижняя граница баланса.
- Команды `Deposit`, `Withdraw`, `Transfer` (перевод атомарен) и журнал `Ledger` с отменой последней операции.

## Что получили

- Все тесты проходят: **98** (59 в `hw01OrderFlow`, 39 в `hw01bank`).
- Написаны собственные тесты: `XmlSalesReportTest`, `ReturnOrderTest`, `OrderReturnTest`, `ConsoleNotifierTest`, `AmountTest`, `AccountTest`, `CommandsTest`, `LedgerTest`; дополнены `SalesReportTest` и `DeliveryTariffTest`.
- Использованы паттерны «Стратегия» (тарифы), «Шаблонный метод» (отчёты), «Состояние» (статусы заказа), «Команда» (операции по счетам).

## Выводы

- Когда знание о варианте поведения лежит в самом варианте (тариф), новый вариант добавляется новым классом, а клиентский код не меняется.
- Шаблонный метод позволил добавить новый формат отчёта одним классом без правок общего алгоритма.
- Состояние, которое само знает свои переходы, делает добавление нового статуса локальным: изменились `OrderStatus`, `Order` и новый сценарий.
- Два вида счёта удобнее выразить данными (граница баланса), чем наследованием: так у `withdraw` один контракт для всех счетов и принцип подстановки не нарушается.
- Команда, которая сама умеет отменяться, освобождает журнал от знания о конкретных операциях.
